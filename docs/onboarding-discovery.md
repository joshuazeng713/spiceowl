# PDK discovery integration

The current implementation is `spiceowl.onboarding.pdk_discovery`. It inspects supplied netlist text and builds a bounded read-only discovery program. It does not contact SSH, select a corner, register a profile, or start a simulation. The onboarding backend owns those steps and keeps path-bearing evidence in private storage.

[`contracts/onboarding-discovery.example.json`](contracts/onboarding-discovery.example.json) contains outputs generated by the actual functions. All input files, identity and resource observations, and platform library bytes are original synthetic fixtures. The environment scanner ran under the existing fixture-only OS/filesystem harness; the PDK program ran in a local Python subprocess. No SSH connection or simulator ran. Absolute paths identify the temporary fixtures that were actually read. Their hashes were checked against those bytes before cleanup; no path or hash was rewritten. These saved observations cannot configure a live host.

## Actual callable API

```python
from spiceowl.onboarding.pdk_discovery import (
    inspect_netlist,
    build_pdk_discovery_script,
    profile_suggestions,
    audit_config_for_candidate,
)

requirements = inspect_netlist(source_text, source_id="input.scs")
program = build_pdk_discovery_script(
    required_masters=requirements["required_masters"],
    roots=currently_observed_private_roots,
    source_sha256=requirements["source_sha256"],
    cds_libs=currently_observed_private_catalogs,
    search_hints=explicit_filename_hints,
)
# The backend executes this program with an explicit host identity, timeout,
# and output limit, then retains its JSON result in the current session.
suggestions = profile_suggestions(discovery)
audit_config = audit_config_for_candidate(
    discovery,
    selected_candidate_id,
    sections=selected_sections,
    tmi_relative_library=selected_platform_library,
)
```

`inspect_netlist` accepts at most 1 MiB of supplied UTF-8 text/bytes and never opens source includes. Its `required_masters` contain unresolved model names; its instance rows retain ordered nets and W/L literals. A numeric dimension is only a source-literal conversion: model scale, legal process dimensions, and scientific intent are not established. The `M` suffix stays unresolved when the language is ambiguous.

`build_pdk_discovery_script` returns Python 2.7/3-compatible source using the standard library. Roots must come from the current environment-discovery session. A `cds.lib` can suggest an additional root, but the scanner does not enlarge its roots automatically. Filename hints only affect search order. Limits can be tightened, never increased beyond the module defaults. Defaults include 256 model files, 256 MiB per file, 1 GiB total read budget, 256 entry candidates, and a result below 2 MiB. The caller still supplies a deadline. `search_policy` records extension, hidden-directory, and symlink scope.

After enumerating directories and before reading model files, the program emits and flushes one progress line: `SPICEOWL_DISCOVERY_DIRECTORY_SNAPSHOT ` followed by JSON and a newline. The trailing ASCII space is part of the exported `DIRECTORY_SNAPSHOT_PREFIX`; `MAX_DIRECTORY_SNAPSHOT_BYTES=65536` bounds the entire line. Its independently hashed receipt has `snapshot:true`, `phase:"directory_inventory"`, `status:"incomplete"`, `search_complete:false`, `results_omitted:true`, empty file/declaration/model-candidate arrays, and `summary.model_files_read:0`. It retains source requirements, roots, limits, actual directory suggestions and traversal statistics. Later model parsing cannot turn this earlier snapshot into model-success evidence.

The transport must recognize this exact prefix separately from the final JSON payload. A verified snapshot can survive a subsequent timeout and offer actual directories for a narrower search; absence of a final result remains an incomplete operation. Validate its source/required-master binding and its own `discovery_id` before presenting it. Do not concatenate the progress line with the final JSON or substitute it for a complete model inventory. The emitter byte-prunes suggestions while preserving request binding. If the fixed request metadata itself cannot fit the progress-line cap, it emits no snapshot and records `directory_snapshot_metadata_limit` in the final result instead of dropping required identity fields.

Directory traversal removes overlapping roots, rotates among independent roots, and uses two breadth-first queues per root. Generic `model`, `models`, `spectre`, `spice`, and `hspice` directory labels, plus explicit search hints, prioritize a subtree without qualifying its contents. Other directories remain searchable under the same existing budget. This prevents one deep OA tree from consuming all visits before another root or a nearby model directory receives a turn. Each root's pending queue is bounded by the existing directory limit.

`traversal` reports `effective_roots`, `requested_root_count`, `directories_scanned`, `pending_directories`, and `overlapping_roots_removed`. `directory_suggestions` contains actual observed in-root directories with `path`, `basis`, `depth`, `scanned`, `qualified:false`, `authorized_for_scan:true`, and `requires_root_confirmation:false`. Bases are `observed_root_child`, `model_directory_name_hint`, `contains_candidate_model_files`, and `unscanned_directory_frontier`. Actual root children have depth 1 and receive retention priority under the same suggestion cap, so the UI can offer observed shallow directories without guessing a parent path. These are candidates for a narrower search, not inferred model identities or recommended corners. `directory_suggestions_truncated` explicitly marks bounded suggestion output. A truncated traversal still has `search_complete=false` even if it found matching masters.

When detailed output exceeds its response budget, the scanner returns `status="incomplete"`, `results_omitted=true`, `search_complete=false`, and empty detailed file/declaration/candidate arrays. It still retains traversal statistics, byte/issue counts, bounded issue codes, and exact observed directory suggestions. Those suggestions prioritize observed root children, followed by model or unscanned-frontier directories and shallow depth, under both the existing count limit and encoded-byte limit. `summary.observed_file_count`, `observed_declaration_count`, `observed_entry_candidate_count`, `observed_graph_node_count`, `observed_include_count`, and `observed_unknown_count` preserve counts before the detailed output was omitted. Empty detailed arrays in this response do not mean that no files or models were found. The final receipt digest is computed over the emitted fallback metadata, and narrowing the scope requires a new discovery rather than treating this receipt as complete.

Before empty-result fallback, the serializer tries omitting only the diagnostic `section_graph` and `includes` arrays. `detail_omissions` records each field and its observed item count. If that fits, all files, declarations, candidates, model contracts, candidate dependency scopes, and original search/issue/ambiguity state remain intact. Omitting diagnostics never changes qualification or promotes an incomplete search. If even this compact representation is too large, fallback `summary.field_bytes` reports each full top-level value's actual UTF-8 JSON byte count; `candidate_field_bytes` aggregates those value sizes by candidate field; `candidate_bytes` reports count/min/max/total candidate sizes. `full_payload_bytes` and `compact_payload_bytes` describe the two attempted encodings. These are counters only and contain no model bodies or paths; encoded-value counts exclude object keys and delimiters.

`profile_suggestions` validates the receipt's consistency digest and returns inert drafts. The digest establishes internal consistency, not remote authenticity or launch-time freshness. The backend must bind the actual server response, supplied source, and user choices to its own current session.

`audit_config_for_candidate` checks the candidate ID and observed section/platform choices and returns input for the existing dependency audit. It does not execute that audit or establish authorization. The subsequent audit must use the final selected combination.

## Entry candidate fields

The discovery receipt uses `schema="spiceowl.pdk-discovery.v1"`. Each `entry_candidates` row has the following fields. These are backend evidence fields; public UI responses should project approved display labels and opaque IDs instead of copying remote paths.

| Field | Meaning |
| --- | --- |
| `candidate_id` | Digest of source requirements, entry, selected candidate scope, dependency scope/file hashes, and TMI observations. Preserve it exactly. |
| `entry_path` | Absolute observed entry/definition file path; private. |
| `entry_sha256` | Digest of the file bytes read during discovery. |
| `section_candidates` | Exact section combination used for this candidate's coverage and model evidence. Currently one source-spelled section or `[null]` for global scope. |
| `available_sections` | Global scope plus source-spelled sections observed in this file. Presence is not a recommendation or compatibility claim. |
| `entry_role` | `include_entry_candidate` when this scope has include edges; otherwise `definition_only`. This is graph evidence, not an executable-profile verdict. |
| `master_coverage` | Required masters visible through the candidate's supported include closure. |
| `missing_masters` | Required masters absent from that closure. |
| `dependency_paths` | Distinct observed files in the closure; private. |
| `dependency_scopes` | Exact `{path, section}` scope rows used for the candidate. Model evidence is bound to these scopes. |
| `coverage_complete` | Required names are covered and the supported closure has no unresolved edges. This does not qualify model semantics or simulation setup. |
| `unknown_codes` | Unresolved scope/dependency conditions that prevent treating the closure as complete. |
| `tmi_candidates` | TMI directory references and their observed platform library options; see below. |
| `models` | Per-required-master static contract evidence; see below. |
| `additional_sections_may_be_required` | Always `true`: discovering a device declaration does not establish all necessary setup sections. |
| `ready_to_run` | Always `false`. |

Discovery also returns `ambiguities`, such as multiple entry/section candidates, split master coverage, duplicate master declarations, missing masters, and multiple TMI platforms. Array order does not select a candidate or imply a recommended corner.

Each `tmi_candidates` row contains:

| Field | Meaning |
| --- | --- |
| `source_path` | Common source file for the group's individually retained TMI declarations; private. |
| `directory` | Resolved observed TMI directory; private. |
| `platform_candidates` | Available `{platform, path, relative_library, sha256, bytes}` rows for immediate child directories containing `libTMImodel.so`. |
| `declarations` | Separate `{line, section, attribute, applied_scopes}` records for every physical declaration in this source file that shares the same directory and platform evidence. No declaration is discarded by grouping. |

Within each declaration, `section` is the exact declaration scope (`null` for a global directive), `line` is the original logical statement's source line, and `attribute` is the observed supported attribute such as `tmipath` or `etmiUsrInput`. `applied_scopes` retains all exact sections of this same source file where the declaration participates in this candidate's closure. These are section labels, not repeated path/section objects. The group header supplies the common source path once.

`relative_library` is the selectable value passed to `audit_config_for_candidate`. It must occur in this candidate's observed platform options. No platform is selected from the UI machine's architecture. A file's presence/hash does not prove binary compatibility; an actual simulator/platform check remains necessary.

Repeated appearances of the same physical TMI declaration deduplicate only when their platform evidence is identical, retaining every applied scope. Common source/directory/platform metadata is then stored once per group, while different source lines, declared sections and attributes remain separate `declarations`. Different source files, directories or platform fingerprints cannot share a group. `platform_candidates` remains in the same location for existing platform-choice and dependency-audit consumers. Contract resolution similarly indexes each physical declaration by source location and wrapper ownership; equal model names in different wrappers or separate declarations remain distinct evidence.

## Model evidence and electrical profile mapping

Each `models` row contains `name`, `polarity`, `ordered_terminal_roles`, `evidence`, `confidence`, `reason`, `needs_confirmation`, and `scope`.

`confidence="verified"` means the finite static parser resolved a source contract within this candidate's exact dependency scopes. It supports explicitly typed recognized MOS model declarations and a wrapper containing exactly one direct MOS call whose four primitive terminals map bijectively to four external ports. The evidence lists declaration locations, the internal instance's ordered nets, the primitive family/type, and the rule used. It never infers polarity from a model name or guesses roles from labels such as `A`, `D`, or `port1`.

Complex or incomplete wrappers, multiple direct devices or model definitions, unknown model families, expressions in polarity selection, duplicated/internal terminal nets, protected/conditional scopes, or missing dependencies cannot become a verified contract. They yield `unknown` or `suggested` with `needs_confirmation=true`. `verified` does not establish process qualification, simulator execution, model scale, legal device dimensions, or the requested experiment's suitability.

The backend can prefill `electrical.models` from verified evidence only when all of these conditions hold:

1. The receipt belongs to the current trusted backend session, host, and supplied source digest; required master names still match that source.
2. `discovery.search_complete` and `candidate.coverage_complete` are true, and `missing_masters` and `unknown_codes` are empty.
3. The final `selected_sections` exactly equal `candidate.section_candidates`, preserving source spelling. Selecting additional/different sections changes the scope and invalidates reuse of the original verified contract.
4. There is exactly one `models` row per required master; every row is `verified`, has `needs_confirmation=false`, has polarity `n` or `p`, and has four distinct roles whose set is `{d, g, s, b}`.

The field mapping is:

```python
electrical_models = {
    model["name"]: {
        "polarity": model["polarity"],
        "terminals": list(model["ordered_terminal_roles"]),
    }
    for model in candidate["models"]
}
```

For example, an external port order `(A B C D)` connected internally as MOS `(B A C D)` produces `terminals=["g", "d", "s", "b"]`. Preserve the returned order; do not replace it with a default. Evidence, paths and confidence fields stay in the onboarding receipt and are not copied into `electrical.models`.

This prefill remains a configuration proposal. The UI can present the model rows as a confirmation table instead of requiring handwritten JSON. Unknown fields need an explicit supported choice or more evidence. If a different/additional section is selected, obtain evidence for that final combination or require explicit model semantics plus a fresh dependency audit. Before registration/use, audit the final entry/sections/platform and bind its actual fingerprints; keep scientific test intent and final profile selection explicit.

The fixture contains three candidates: the device-definition file and two named entry sections. All have finite static model evidence, but neither an entry nor a platform is selected. It is suitable for UI selection/table rendering and ambiguity handling, not a real setup or simulation test.
